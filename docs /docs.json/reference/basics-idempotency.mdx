---
title: "Идемпотентность"
---

Повторный вызов создающего эндпоинта **не должен создавать второй объект**. Иначе обычный сетевой
таймаут (ответ потерялся, хотя платёж уже создан) обернётся дублем — вторым счётом или второй выплатой.

Защититься можно двумя способами — они работают вместе.

## 1. Заголовок `Idempotency-Key` (рекомендуемый)

Пошлите на создающем запросе заголовок с любым уникальным значением:

```
Idempotency-Key: 3f9a1c2e-…
```

Повтор **с тем же значением** вернёт **тот же** ответ (тот же объект, тот же HTTP-код), а не создаст
второй объект. В ответе на повтор придёт `Idempotent-Replayed: true`.

Правила:
- ключ должен быть **одинаковым во всех попытках** одного логического действия (генерируйте его
  **до** первой отправки, а не на каждую попытку);
- на разные действия — **разные** ключи;
- ключ действует в пределах вашего мерчанта; максимум 255 символов;
- если запрос с этим ключом ещё выполняется, повтор получит `409 idempotency.in_progress` — повторите
  чуть позже.

<Note>
  **Пользуетесь нашим [SDK](/sdk/overview) (v1.1.0+)?** Он шлёт этот заголовок сам и держит его
  одинаковым во всех внутренних повторах — специально ничего делать не нужно. Свой ключ можно задать
  через `idempotency_key`.
</Note>

## 2. `order_id` (ваш бизнес-ключ)

Независимо от заголовка, создающие операции дедуплицируются по вашему `order_id`:

| Операция | Ключ идемпотентности | Поведение при повторе |
|---|---|---|
| [Платежи](/reference/payment-create) | `order_id` (в паре с мерчантом) | Вернётся тот же инвойс, а не создастся второй. |
| [Выплаты](/reference/payout-create) | `order_id` — **обязателен** | Вернётся уже существующая выплата. |
| [Возвраты](/reference/payment-refund) | пара `(платёж, адрес, сумма)` | Вернётся уже созданный возврат. |
| [Статические кошельки](/reference/wallet-create) | тройка `(currency, network, order_id)` | Вернётся тот же адрес. |
| [Перевод на личный кошелёк](/reference/transfer-to-personal) | `order_id` | Повтор — no‑op. |
| [Батчи](/reference/payment-batch) | `Idempotency-Key` на весь батч + ключ каждого элемента | Повтор батча не создаст вторую пачку; элементы дедуплицируются по своим `order_id`. |

Для платежей `order_id` не обязателен — но **без него и без заголовка** повтор создаст второй счёт.
Так что задавайте хотя бы одно из двух.

---

## Почему подписи недостаточно

Подпись запроса защищает от подмены и от переигрывания **старше 5 минут**, но у неё есть окно
±5 минут (см. [Аутентификация](/reference/basics-auth)). Внутри этого окна перехваченный запрос технически
можно переиграть. Реальную защиту от дублей даёт `Idempotency-Key` или `order_id`.

<Note>
  **Никогда не создавайте платёж/выплату «голым» запросом.** Хотя бы одно из двух: заголовок
  `Idempotency-Key` (одинаковый во всех попытках) **или** ваш `order_id`. Иначе повтор при таймауте
  приведёт к дублю — второму счёту или второй выплате. Для выплат `order_id` обязателен всегда.
</Note>

---

## Защита от гонки

Для платежей проверка‑и‑создание защищены advisory‑локом по паре `(merchant, order_id)`. Два
одновременных запроса с одним `order_id` не создадут два счёта — второй дождётся первого и получит тот
же объект.

---

## Нюанс: терминальные объекты не блокируют создание

Идемпотентность действует, пока по ключу есть **живой** объект. Если предыдущий счёт по этому
`order_id` уже терминальный или просрочен, повторный `POST /v1/payment` создаст **новый** счёт (если
только вы не используете `is_refresh` — см. [`POST /v1/payment`](/reference/payment-create)).
